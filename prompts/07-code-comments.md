# 📝 ۷. کیفیت کد و قانون کامل کامنت‌نویسی

[↩ بازگشت به پرامپت مادر](../PROMPT.md) · [آزمون و معیار پذیرش](06-testing-acceptance.md) · [موتور هندسه](03-parametric-geometry.md)

## ۷.۱. هدف و اصل پایه

کد باید برای توسعه‌دهندهٔ بعدی قابل فهم، بررسی و اصلاح باشد. کامنت حرفه‌ای باید **چیزی را روشن کند که از خود کد، نام‌گذاری یا نوع‌ها به‌آسانی فهمیده نمی‌شود**: دلیل تصمیم، فرض، واحد، invariant، محدودیت موتور، منشأ داده، پیامد امنیتی یا دلیل یک راه‌حل.

> «کامنت‌نویسی کامل» به معنی نوشتن توضیح برای تک‌تک خطوط نیست. کامنت‌گذاریِ خط‌به‌خطِ بدیهیات، کد را شلوغ و تغییر آن را پرخطر می‌کند. هدف، پوشش کاملِ قراردادها و منطق غیرآشکار است؛ نه زیادکردن شمار کامنت‌ها.

## ۷.۲. زبان، لحن و قالب

- زبان توضیح‌های کد در این پروژه **فارسیِ روشن و فنی** باشد. نام کلاس، متد، متغیر و API طبق قرارداد زبان برنامه‌نویسی و به انگلیسی باقی بماند.
- اصطلاح استانداردی که ترجمه‌اش مبهم است، بار اول با معادل فارسی و عبارت انگلیسی/اختصار بیاید؛ نمونه: «پیشروی رزوه (lead)». پس از آن از واژه‌نامهٔ یکسان پروژه استفاده کن.
- جمله‌ها دقیق، کوتاه و بی‌طرف باشند. از شوخی، طعنه، متن گفت‌وگویی، توضیح «این کد را AI نوشته» و عبارت نامشخصی مثل «کارهای لازم را انجام می‌دهد» پرهیز کن.
- کامنت درست **بالای** بخش مربوط قرار گیرد. trailing comment کنار هر خط فقط وقتی مجاز است که به خواندن یک ثابت/واحدِ غیرآشکار کمک کند.
- قراردادِ `///`، `//` و `/* ... */` را مطابق جدول پایین رعایت کن. توضیح XML باید با formatter و build سازگار باشد.
- در فایل متنیِ چندزبان، encoding استاندارد UTF-8 و حروف فارسی درست حفظ شود.

## ۷.۳. چه چیزی باید مستند شود؟

| محل | قاعدهٔ کامنت |
|---|---|
| API عمومی | هر کلاس، interface، enum، record، property و متد عمومی، توضیح XML داشته باشد؛ هدف، قرارداد، ورودی/خروجی، واحد و استثناهای مهم را ثبت کن |
| مدل‌های دامنه | معنای پارامترها، واحد پایه، مقدار «تعریف‌نشده»، invariant و ارتباط پارامترها را توضیح بده |
| الگوریتم مهندسی | فرمول یا منطق غیرآشکار، فرض ورودی، علامت‌ها، واحدها، محدودیت تقریب و منبع/نسخهٔ مرجع مجاز را ثبت کن |
| CAD و هندسه | محور/مبدأ، handedness، جهت sweep، pitch در برابر lead، داخلی/خارجی، تلرانس، winding/normals، اعتبارسنجی و محدودیت موتور را توضیح بده |
| منطق پیچیده | دلیل الگوریتم، edge case، حالت شکست، مصالحهٔ کارایی/دقت و دلیل انتخاب راه‌حل را بنویس |
| کد async و هم‌زمان | thread affinity، ترتیب انتظار، cancellation، thread-safety، re-entrancy، ownership و عمر منبع native را مستند کن |
| ورودی/خروجی فایل | فرمت/واحد، قرارداد محور، رفتار overwrite، نوشتن اتمیک، محدودیت اندازه، اعتبارسنجی و پیامدهای امنیتی را ثبت کن |
| ذخیره و migration | schema/version، سازگاری رو به عقب، تبدیل واحد، دادهٔ nullable، نگهداری اطلاعات ناشناخته و rollback را توضیح بده |
| حریم خصوصی/امنیت | دلیل redaction، محل امن ذخیرهٔ credential، شرط رضایت، TLS، حداقل‌سازی داده یا محدودیت parser را بدون درج secret شرح بده |
| دادهٔ استاندارد/کاتالوگ | منبع، نسخه/ویرایش، تاریخ بازبینی و مجوز/محدودیت استفاده را در metadata مناسب ثبت کن؛ متن دارای حق نشر را داخل کامنت بازنشر نکن |
| آزمون‌ها | هدف رفتاری، regression یا edge case مورد پوشش را توضیح بده؛ نام آزمون تا حد ممکن خودش رفتار را بیان کند |
| تصمیم موقت | علت محدودیت و شرایط حذف/جایگزینی آن را ثبت کن؛ شناسهٔ مسئله یا TODO استاندارد داشته باشد |

## ۷.۴. قرارداد XML docs برای C#/.NET

اگر برنامه با C#/.NET ساخته می‌شود:

1. برای هر API عمومی از XML documentation (`///`) استفاده کن.
2. دست‌کم `<summary>` را برای همهٔ اعضای عمومی بنویس. برای متدهای دارای ورودی/خروجی از `<param>` و `<returns>`، برای استثناهای مهم از `<exception>`، و برای قیدها/واحد/محدودیت موتور از `<remarks>` استفاده کن.
3. از `<see cref="..."/>`، `<paramref name="..."/>` و `<typeparam>` در جای مناسب استفاده کن؛ متن را به شکل HTML یا XML نامعتبر ننویس.
4. دربارهٔ propertyهای عددی، واحدِ ذخیره‌شده و قرارداد nullable را مشخص کن. نامی مثل `Diameter` اگر واحدش از نوع/نام معلوم نیست باید صریحاً مستند شود.
5. `<example>` را برای API پیچیده و پرتکرار اضافه کن؛ مثال باید کامپایل‌پذیر یا آشکارا شبه‌کد باشد و مقدار مهندسی ساختگی را استاندارد جا نزند.
6. در صورت فعال‌بودن تولید فایل XML docs، build را بررسی کن. warningهای مستندسازی عمومی را یا برطرف کن یا برای نوع موردنظر، دلیلِ استثنا را مستند کن؛ برای خاموش‌کردن سراسری warningها صرفاً برای سبزشدن build اقدام نکن.
7. اعضای private/internal هم در صورت داشتن الگوریتم پیچیده، خطر native/threading، قرارداد واحد یا تصمیم غیرآشکار با کامنت معمولی مستند شوند؛ برای getter/setter بدیهی کامنت زائد ننویس.

### نمونهٔ مناسب

```csharp
/// <summary>
/// قطر اسمی رزوه را در واحد پایهٔ میلی‌متر نگه می‌دارد.
/// </summary>
/// <remarks>
/// ورودی رابط می‌تواند اینچ باشد؛ تبدیل باید پیش از ساخت مدل انجام شود.
/// این مقدار به‌تنهایی قطر گام یا قطر ریشه را تعیین نمی‌کند.
/// </remarks>
public double NominalDiameterMm { get; init; }

/// <summary>
/// پیشروی رزوه را بر اساس گام و تعداد شروع‌ها محاسبه می‌کند.
/// </summary>
/// <param name="pitchMm">فاصلهٔ محوری میان دو دندانهٔ مجاور، برحسب میلی‌متر.</param>
/// <param name="starts">تعداد شروع‌های مستقل رزوه؛ باید حداقل یک باشد.</param>
/// <returns>پیشروی محوری در یک دور کامل، برحسب میلی‌متر.</returns>
/// <exception cref="ArgumentOutOfRangeException">
/// اگر گام مثبت نباشد یا تعداد شروع‌ها کمتر از یک باشد.
/// </exception>
public static double CalculateLeadMm(double pitchMm, int starts)
```

### نمونهٔ مناسب برای منطقِ غیرآشکار

```csharp
// در رزوهٔ چندشروع، فاصلهٔ یک دور کامل برابر گام ضرب‌در تعداد شروع‌هاست؛
// مسیر sweep از محور محلیِ قطعه استفاده می‌کند تا تغییر جهت نمایش، هندسه را وارونه نکند.
var leadMm = pitchMm * starts;
```

این مثال فقط قرارداد توضیح است؛ فرمول و پیاده‌سازی واقعی باید با مدل داده و منبع هندسیِ برنامه تطبیق داده شود.

### اگر فناوری دیگری انتخاب شد

اگر بعد از بررسی، زبان دیگری به‌جای C# انتخاب شد، همان سطح از پوشش را با قالب رسمی همان اکوسیستم پیاده کن: docstring استاندارد برای API عمومی در Python، JSDoc برای JavaScript/TypeScript، مستندات rustdoc برای Rust یا معادل پذیرفته‌شدهٔ زبان منتخب. الزام محتوایی تغییر نمی‌کند: هدف، ورودی/خروجی، واحد، invariant، خطا و محدودیت باید مستند باشد. ابزار مستندسازیِ انتخاب‌شده را در README توسعه‌دهندگان توضیح بده.

## ۷.۵. کامنت‌های هندسه و محاسبات مهندسی

در هر الگوریتم هندسی/ریاضی که از روی نام متغیر به‌تنهایی قابل بازسازی نیست، این پرسش‌ها باید پاسخ بگیرند:

- زاویه بر حسب درجه است یا رادیان؟ نقطهٔ مرجع و جهت مثبت چیست؟
- مقدار در میلی‌متر است، اینچ، یا واحد داخلی موتور؟ در چه مرزی تبدیل انجام می‌شود؟
- قطر اسمی، قطر گام، قطر بزرگ/کوچک و شعاع با هم اشتباه نشده‌اند؟
- `pitch` فاصلهٔ دو رزوهٔ مجاور است یا `lead` در هر دور؟ تعداد شروع‌ها کجا لحاظ می‌شود؟
- راست‌گرد/چپ‌گرد، رزوهٔ داخلی/خارجی، محور محلی/جهانی و جهت سطح‌ها چگونه تعریف شده‌اند؟
- تلرانس عددی هستهٔ CAD با تلرانس ساخت/فیت چاپ یکی فرض نشده است؟
- هندسه در چه محدوده‌ای معتبر است و موتور در کدام edge case شکست می‌خورد؟
- اگر عدد از یک جدول/استاندارد آمده، منبع و ویرایش کدام است و آیا استفاده از داده مجاز است؟

واحد را تا حد ممکن در نوع‌ها یا نام‌ها encode کن (مانند `LengthMm`, `AngleDegrees`, `PitchMm`) تا کامنت تنها سد خطای واحد نباشد. کامنت نمی‌تواند API مبهم یا طراحیِ دارای اشتباه واحد را توجیه کند.

## ۷.۶. کامنت حریم خصوصی، شبکه و امنیت

- توضیح بده **چرا** داده‌ای redacted می‌شود، کجا credential نگهداری می‌شود، کدام transport مجاز است و رضایت کاربر چگونه بررسی می‌شود؛ جزئیات اجرایی لازم برای بازبینی امنیتی را حذف نکن.
- رمز، App Password، OAuth token، SMTP/API key، شمارهٔ کارتِ کاملِ کاربر، اطلاعات واقعیِ آزمایش یا دادهٔ شخصی را در کامنت، fixture، screenshot، log یا message ننویس.
- اگر تنظیمِ حساس در سیستم عامل ذخیره می‌شود، کامنت به سازوکار واقعی (Credential Manager/DPAPI) و رفتار خطا اشاره کند؛ هرگز ادعا نکند که مقدار رمزگذاری شده وقتی در عمل plaintext است.
- دربارهٔ parser فایل/ZIP، مجوزها و سقف اندازه، comment باید فرضِ ورودی غیرقابل اعتماد و علت محدودیت را روشن کند.
- کامنت TLS را راهنمای خاموش‌کردن certificate validation نکن؛ راه‌حل insecure برای دورزدن خطا ممنوع است.

## ۷.۷. آزمون، رابط کاربری و داده

- در آزمون، کامنتِ بالای تست باید رفتار یا regressionِ دشوارفهم را مشخص کند؛ از کامنتی مثل «این تست را اجرا می‌کند» پرهیز کن.
- برای دادهٔ مرجع، comment/metadata باید منشأ و نسخه را نشان دهد؛ اگر مقدار صرفاً fixture است بنویس `صرفاً دادهٔ آزمایشی — استاندارد نیست`.
- متن UI در resource/localization نگهداری شود؛ کامنت کنار رشته فقط دربارهٔ placeholder، pluralization، RTL، واحد یا دلیل دسترس‌پذیری باشد، نه تکرار ترجمه.
- در XAML، کامنت برای مرزبندی بخش پیچیده، resource، binding غیرآشکار یا تصمیم accessibility باشد؛ برای هر control توضیح بدیهی تکرار نکن.
- در migration یا schema، سازگاری نسخهٔ قبلی و دلیل تغییر را ذکر کن؛ comment را تنها منبع schema قرار نده.
- در فایل auto-generated یا خروجی ابزار، کد تولیدشده را دستی اصلاح نکن و کامنتی که generator از بین می‌برد به آن اضافه نکن؛ منبع تولید را اصلاح کن.

## ۷.۸. TODO، FIXME و کامنت منسوخ

- `TODO`، `FIXME`، `HACK` یا `BUG` تنها وقتی مجاز است که مسئله، علت موقت‌بودن، شرط حذف و شناسهٔ قابل پیگیری داشته باشد؛ نمونه: `TODO(SSND-123): ...`.
- TODO مبهم مثل «بعداً درست شود»، کد کامنت‌شدهٔ بلااستفاده و یادداشت بدون مالک/معیار حذف باقی نماند.
- کامنت بخشی از کد است: هر تغییر منطقی، واحد، قرارداد یا رفتار باید کامنت مرتبط را هم به‌روزرسانی کند. کامنت خلاف کد از نبود کامنت بدتر است.
- پیش از تحویل، TODOها و commentهای قدیمی/متناقض را جست‌وجو کن و موارد حل‌نشده را در گزارش وضعیت ذکر کن.

## ۷.۹. نمونهٔ بد و اصلاح آن

**بد — بازگویی بدیهیات:**

```csharp
// مقدار را یکی زیاد می‌کند
count++;
```

**بهتر — نام خوب، بدون کامنت زائد:**

```csharp
count++;
```

**بد — واحد و دلیل نامعلوم:**

```csharp
// calculate
var x = a * b;
```

**بهتر — وقتی تصمیم واقعاً غیرآشکار است:**

```csharp
// قطر نهایی باید برحسب میلی‌متر باشد؛ b ضریب تبدیل از واحد ورودی به واحد پایه است.
var diameterMm = inputDiameter * millimetersPerInputUnit;
```

در کد نهایی، اگر نام متغیرها یا typeها ابهام را رفع می‌کنند، آن‌ها را بهبود بده؛ کامنت را جایگزین نام‌گذاری روشن نکن.

## ۷.۱۰. کنترل کیفیت و چک‌لیست بازبینی

پیش از merge/تحویل هر بخش، این پرسش‌ها را بررسی کن:

- [ ] آیا API عمومیِ اضافه یا تغییرکرده XML docs فارسی و دقیق دارد؟
- [ ] آیا واحد، محور، جهت، علامت، range و nullable در قراردادهای فنی روشن‌اند؟
- [ ] آیا منطق غیرآشکار، مصالحه، محدودیت engine و دلیل workaround توضیح داده شده است؟
- [ ] آیا comment با رفتار واقعی کد همخوان و پس از تغییر به‌روز است؟
- [ ] آیا کامنتی فقط متن کد را تکرار می‌کند یا در هر خط کامنت زائد وجود دارد؟ آن را حذف/اصلاح کن.
- [ ] آیا هیچ secret، دادهٔ خصوصی، شماره کارت یا دادهٔ واقعی کاربر در comment/test/log وجود دارد؟
- [ ] آیا TODO/FIXME شناسه و معیار حذف دارد؟ آیا کد کامنت‌شدهٔ بی‌استفاده حذف شده است؟
- [ ] آیا build/analyzer/formatter روی XML docs و encoding فارسی اجرا شده است؟

در صورت وجود analyzer یا formatter مناسب، آن را در build/test مستند کن. ابزار خودکار جای بازبینی فنی را نمی‌گیرد و نباید با خاموش‌کردن ruleها، کمبود مستندات را پنهان کرد.
