# 🧪 ۶. آزمون‌ها، معیار پذیرش و تحویل

## ۶.۱. روش کار و گزارش آزمون

- آزمون را همراه هر قابلیت اضافه کن؛ build سبز به‌تنهایی معیار کیفیت نیست.
- آزمون‌های unit برای دامنه/اعتبارسنجی، integration برای موتور هندسه و فایل‌ها، UI برای مسیرهای کلیدی، و smoke test نصب/اجرا در Windows داشته باش.
- نتیجه‌ها را با فرمان اجرا، محیط، نسخهٔ runtime، تعداد pass/fail/skip و محدودیت‌ها گزارش کن.
- آزمون‌هایی که در محیط فعلی اجرا نمی‌شوند (مثلاً اجرای WPF یا اعتبارسنجی در نرم‌افزار CAD تجاری)، `تأییدنشده` اعلام کن؛ از جعل screenshot/نتیجه خودداری کن.
- fixtureها باید دادهٔ ساختگیِ مشخصاً آزمایشی و بدون اطلاعات شخصی/credential باشند.

## ۶.۲. ماتریس آزمون دامنه و رزوه

| شناسه | آزمون | نتیجهٔ مورد انتظار |
|---|---|---|
| GEO-01 | ساخت پیچ ساده با رزوهٔ متریکِ شناخته‌شده و طول/قطر معتبر | مدل ساخته می‌شود؛ پارامترها و واحد در پیش‌نمایش و فایل بومی حفظ می‌شوند |
| GEO-02 | ساخت مهره با رزوهٔ هم‌خانواده/هم‌اندازه | مدل و حفرهٔ داخلی واقعی یا حالتِ فاقد رزوه با برچسب صادقانه نمایش داده می‌شود |
| GEO-03 | جفت پیچ+مهره با قطر/گام/جهت سازگار | برنامه سازگاری را گزارش می‌کند؛ مدل‌ها جدا و قابل انتخاب‌اند |
| GEO-04 | تغییر گام، جهت راست/چپ، تعداد شروع و طول رزوه | مدل مطابق پارامترهای تغییرکرده بازتولید می‌شود؛ lead با pitch اشتباه نمی‌شود |
| GEO-05 | رزوهٔ داخلی/خارجی، پروفیل سفارشی و مقطع نامعتبر | حالت‌های پشتیبانی‌شده درست ساخته؛ پروفیل self-intersection/نامعتبر با علت رد می‌شود |
| GEO-06 | نوع‌های مختلف سر، درایو، نوک، مهره و واشر | پارامترهای نوعی قابل استفاده‌اند؛ ویژگی ناممکن بی‌صدا حذف نمی‌شود |
| GEO-07 | مقدار صفر/منفی، NaN، Infinity، مقدار بسیار بزرگ، قطر یا طول ناسازگار | ورودی قبل از ساخت رد می‌شود؛ خطای فارسی و قابل اقدام دارد |
| GEO-08 | تبدیل میلی‌متر ↔ اینچ، ارقام فارسی/لاتین، اعشار و کسر اینچ | مقدار واقعی/ابعاد حفظ می‌شود؛ تبدیل تکراری خطای تجمعیِ ناموجه ایجاد نمی‌کند |
| GEO-09 | تغییر پارامتر در حین تولید سنگین و لغو عملیات | UI responsive می‌ماند؛ نتیجهٔ قدیمی به‌جای مدل جدید نشان داده نمی‌شود |
| GEO-10 | ذخیره و بازکردن پروژهٔ فارسی، پروژهٔ قدیمی و پروژهٔ ناقص | متن/پارامتر حفظ یا migration مستند انجام می‌شود؛ فایل خراب پیام امن می‌دهد |

برای مقادیر «استاندارد»، آزمون مرجع باید مشخص کند منبع معتبر چیست. آزمونِ دادهٔ تصادفی یا یک screenshot به‌تنهایی اثبات انطباق استاندارد نیست.

## ۶.۳. ماتریس خروجی و چاپ

| شناسه | آزمون | نتیجهٔ مورد انتظار |
|---|---|---|
| EXP-01 | خروجی STEP AP242 از مدل CAD معتبر | فایل parse/round-trip می‌شود؛ جسم، ابعاد، واحد و اجزا تا حد موتور حفظ می‌شوند |
| EXP-02 | خروجی STL/OBJ/3MF با presetهای کم و زیاد | فایل‌ها ساختار معتبر، مقیاس درست و کیفیتِ متفاوتِ قابل‌اندازه‌گیری دارند |
| EXP-03 | بررسی مشِ چاپ | نرمال‌ها و تعداد وجه معتبر؛ manifold/watertight/self-intersection طبق توان ابزار گزارش می‌شوند |
| EXP-04 | خروجی به مسیر نامعتبر، read-only یا دیسک پر | پیام فارسی روشن؛ فایل قبلی سالم می‌ماند؛ فایل نیمه‌کاره جا نمی‌ماند |
| EXP-05 | فایل مقصد موجود است | overwrite فقط پس از تأیید کاربر انجام می‌شود |
| EXP-06 | پروفایل چاپ با لقی‌ها/جبران‌های مختلف | نسخهٔ چاپی متفاوت و مقدار تغییرها قابل مشاهده؛ مدل اسمی دست‌نخورده می‌ماند |
| EXP-07 | چاپ روی ترکیب نامعتبر/دیوارهٔ نازک | هشدار/خطا علت را مشخص می‌کند؛ خروجیِ خراب موفق گزارش نمی‌شود |
| EXP-08 | ذخیره/بازشدن `.ssnd` | پارامتر، واحد، استاندارد، پروفایل چاپ، version و قطعات بازسازی می‌شوند؛ secret/شماره کارت وجود ندارد |
| EXP-09 | فرمت غیرفعال/وابسته به مجوز | رابط دلیل محدودیت را می‌گوید؛ پسوند جعلی یا فایل صفر بایت تولید نمی‌شود |

حداقل یک مسیر مستقل برای بررسی فایل خروجی به‌کار ببر؛ اگر import مجدد با همان کتابخانه است، این موضوع را در گزارش ذکر کن.

## ۶.۴. آزمون UI و فارسی

- رابط پیش‌فرض کاملاً فارسی و راست‌چین است؛ متن در دکمه، tooltip، منو، پیام، نصب‌کننده و فرم خطا ترجمه‌نشده باقی نمی‌ماند.
- فونت وزیرمتن در Windows تمیز/بدون نصب سیستم درست رندر می‌شود؛ مجوز آن در بسته وجود دارد.
- رقم، ممیز، واحد، نقطه/ویرگول و کدهای ASCII در ورودی RTL به‌هم نمی‌ریزند.
- مسیر و نام فایل فارسی، فاصله، نام طولانی و نویسهٔ مجاز Windows با ذخیره و خروجی کار می‌کند.
- کنترل‌های کلیدی با صفحه‌کلید/Tab قابل دسترس‌اند؛ focus و ترتیب در RTL درست است.
- پنجره در مقیاس Windows 125٪ و 200٪ یا اندازهٔ متن بزرگ، فرم‌ها و پیش‌نمایش را خارج از قاب نمی‌برد.
- وضعیت‌ها فقط رنگی نیستند؛ متن و آیکون واضح برای موفقیت، هشدار، خطا، offline، queued و sending وجود دارد.
- متن خطا برای کاربر فارسی قابل فهم است و stack trace خام فقط در log فنی پاک‌سازی‌شده ثبت می‌شود.

## ۶.۵. آزمون آفلاین، ایمیل و حریم خصوصی

| شناسه | سناریو | نتیجهٔ مورد انتظار |
|---|---|---|
| NET-01 | اجرای اولیه با قطع کامل شبکه | برنامه باز می‌شود؛ ساخت، پیش‌نمایش، ذخیره و خروجی محلی کار می‌کند |
| NET-02 | بررسی درخواست‌های شبکه در اجرای معمول | درخواست پنهانی، telemetry یا update check بدون رضایت وجود ندارد |
| MAIL-01 | ارسال گزارش وقتی offline است | پیام به‌صورت محلی صف می‌شود؛ وضعیت «ارسال نشده/در انتظار اتصال» است |
| MAIL-02 | SMTP/API تنظیم نشده | گزارش حفظ/قابل حذف است؛ برنامهٔ ایمیل باز نمی‌شود؛ موفقیت کاذب نشان داده نمی‌شود |
| MAIL-03 | ارسال پس از opt-in، تنظیم سرویس معتبر و اتصال | ارسال امن با TLS؛ فقط پس از تأیید واقعی transport وضعیت «ارسال شد» ثبت می‌شود |
| MAIL-04 | گواهی TLS نامعتبر یا credential غلط | اتصال fail-closed؛ خطای قابل فهم، بدون fallback به plaintext و بدون افشای secret |
| MAIL-05 | opt-in خاموش یا کاربر ارسال را لغو می‌کند | هیچ ایمیلی ارسال نمی‌شود؛ صف/گزارش قابل پاک‌کردن است |
| PRIV-01 | بررسی payload/log/پروژه | شماره کارت، رمز، توکن، نام کاربری، مسیر فایل خصوصی و کل پروژه به‌طور پیش‌فرض وجود ندارد |
| PRIV-02 | شماره کارت در صفحهٔ حمایت | در حالت اولیه پوشیده است؛ نمایش/کپی با اقدام؛ شماره در گزارش و فایل پروژه نیست |
| SEC-01 | بازکردن ZIP/پروژهٔ دستکاری‌شده | ورودی validate، محدودیت اندازه/مسیر اعمال و خطای امن نمایش داده می‌شود |

ایمیل هم‌زمان با نبود اینترنت ممکن نیست. آزمون‌ها باید نشان دهند core offline است و مسیر ارسال صرفاً زمانی عمل می‌کند که شرط‌های رضایت، پیکربندی و شبکه فراهم باشند.

## ۶.۶. عملکرد و پایداری

- عملیات helical thread و export نباید UI را برای مدت طولانی قفل کند؛ پیشرفت/لغو و مدیریت خطا وجود داشته باشد.
- برای یک مدل متعارف، زمان build، مصرف حافظه و تعداد وجه در presetهای مختلف ثبت شود؛ هدف‌های عددی پس از اندازه‌گیری روی ماشین مرجع تعریف شوند، نه حدس.
- درخواست خروجی تکراری/لغو میان عملیات، تغییر فرم در حین تولید و بازکردن چند پروژه آزمون شود.
- crash یا شکست موتور هندسه به خرابی فایل قبلی/تنظیمات منجر نشود؛ crash recovery برای پروژهٔ ذخیره‌نشده طبق طراحی تست شود.
- گزارش خطا به خرابی ثانویه منجر نشود؛ اگر ذخیرهٔ صف یا شبکه شکست خورد، برنامهٔ اصلی قابل استفاده بماند.

## ۶.۷. بازبینی کد و کامنت‌نویسی

- قانون کامل [کیفیت کد و کامنت‌نویسی](07-code-comments.md) در تمام کد جدید/تغییریافته رعایت شود.
- API عمومیِ C# مستندات XML فارسیِ معتبر داشته باشد؛ build/formatter/analyzer مربوط اجرا شود و warningهای بی‌دلیل با خاموش‌کردن ruleها پنهان نشوند.
- برای الگوریتم‌های هندسه، قرارداد واحد/محور/جهت/تلرانس و تفاوت pitch/lead مستند باشد؛ تست‌های مرزی این قراردادها را کنترل کنند.
- کامنت‌ها رفتار واقعی را توضیح دهند، بدیهیات را تکرار نکنند و پس از تغییر منطق به‌روز شوند.
- بازبینی منبع برای commentهای منسوخ، TODO/FIXME بی‌مسئله، کد کامنت‌شده و secret/اطلاعات خصوصی انجام شود.
- یک check-list یا analyzer سبک در فرایند review به‌کار رود؛ ابزار خودکار به‌تنهایی کیفیت معنا را تضمین نمی‌کند.

## ۶.۸. نصب و تحویل Windows

- روی Windows 10/11 x64 واقعی، نصب تمیز، اجرای بدون اینترنت، فونت، viewport، ذخیره/بازکردن، خروجی، ارتقا و حذف آزمون شوند.
- اگر برنامه self-contained است، Runtime و وابستگی native همراه package باشند؛ اگر نیست، نیاز Runtime و نصب آفلاین آن واضح و در بستهٔ جداگانه فراهم باشد.
- نصب‌کننده از اینترنت فایل نگیرد؛ نسخه/ناشر، مسیر نصب، shortcut، محل فایل داده و امکان uninstall مشخص باشد.
- اسکن حداقلی مجوزها/آسیب‌پذیری dependency و اندازهٔ بسته ثبت شود؛ build release با build توسعه اشتباه نشود.
- مستندات فارسی شامل نیازمندی سیستم، نصب آفلاین، کار با رزوه، خروجی/کیفیت، تنظیم SMTP با هشدار حریم خصوصی، بازیابی/backup و عیب‌یابی باشد.

## ۶.۹. معیار پذیرش نسخه

نسخه فقط وقتی «قابل پذیرش» است که تمام موارد تحویل‌شده واقعاً کار کنند و این موارد وضعیت روشن داشته باشند:

- [ ] برنامه با نام فارسی/انگلیسی، فارسی‌سازی و فونت وزیرمتن همراه اجرا می‌شود.
- [ ] دست‌کم یک جریان کاملِ پیچ و یک جریان کاملِ مهره از ورود پارامتر تا پیش‌نمایش و ذخیره کار می‌کند.
- [ ] ابعاد/واحد/رزوه اعتبارسنجی می‌شوند و خطاها برای کاربر توضیح دارند.
- [ ] پروژهٔ بومی قابل بازکردن و ویرایش مجدد است.
- [ ] هر فرمتِ فهرست‌شده به‌عنوان پشتیبانی‌شده، فایل معتبرِ آزموده‌شده تولید می‌کند؛ بقیه واضح علامت‌گذاری شده‌اند.
- [ ] اصلاح چاپ جداگانه، قابل تنظیم و قابل مقایسه است؛ مدل اسمی تغییر ناخواسته ندارد.
- [ ] امکانات محلی در حالت قطع شبکه کار می‌کنند؛ ایمیل هرگز بدون اینترنت، پیکربندی و رضایت ادعای ارسال نمی‌کند.
- [ ] دادهٔ حساس در پروژه، log و گزارش نیست؛ شمارهٔ حمایت با نمایش/کپیِ آگاهانه ارائه می‌شود.
- [ ] build، آزمون‌های موجود، مجوزهای وابستگی و محدودیت‌های محیط در گزارش پایانی آمده‌اند.
- [ ] هیچ قابلیت، استاندارد، فرمت یا آزمونی صرفاً به‌خاطر وجود دکمه/متن در UI «تکمیل» نامیده نمی‌شود.
- [ ] قانون کامنت‌نویسی رعایت شده: API عمومی مستند، منطق غیرآشکار توضیح‌داده، commentها به‌روز، و کامنت بدیهی/secret/TODO بی‌ردیابی وجود ندارد.

## ۶.۱۰. گزارش تحویل عامل

در پایان کار، پاسخ عامل باید این بخش‌ها را داشته باشد:

1. خلاصهٔ کوتاه و روشن از آنچه واقعاً ساخته شد.
2. دستور اجرای محلی و فرمان‌های build/test، با نتیجهٔ هرکدام.
3. جدول قابلیت‌ها و وضعیت `تکمیل / آزموده / محدود / برنامه‌ریزی‌شده`.
4. فرمت‌های خروجیِ واقعی و روش آزمودن/بازکردن آن‌ها.
5. پیش‌نیازهای نصب و اینکه آیا فایل نصب کاملاً آفلاین است.
6. محدودیت‌های فنی، داده/مجوزهای نیازمند تصمیم و آزمون‌های انجام‌نشده.
7. نحوهٔ فعال‌سازی گزارش ایمیل و توضیح اینکه ارسال در نبود اینترنت ممکن نیست.
